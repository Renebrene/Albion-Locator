# Albion Locator Autonom — техническое описание

**Актуальность:** 18 октября 2026 г.

**Назначение документа:** описывает активную сборку проекта в репозитории. Запускаемая точка входа — `src/main.py`, основная веб-страница — корневой `static/index.html`. В репозитории присутствуют архивные и устаревшие копии; они не являются активной сборкой.

## 1. Назначение

Albion Locator Autonom — локальное веб-приложение для работы с точками и дорогами Ростовской области. Пользователь выбирает точку на карте, вводит координаты, использует GPS-данные фотографии, находит адрес через онлайн-подсказки или задаёт километраж дороги из установленного локального индекса. Приложение получает ближайшую дорожную геометрию и показывает её характеристики и расстояние до точки.

В приложении также есть учётные записи с ролями, история/закладки, пакетное извлечение GPS из фотографий, сохранение снимков карты, локальный поиск по SQLite и предварительный преобразователь WGS84 ↔ МСК-61.

**Текущая поставка не является полностью автономной:** приложение может работать в локальной сети, но основной сценарий адресного поиска, внешних дорог, подложки и нескольких frontend-библиотек зависит от сети. Локальные наборы адресов/дорог, MBTiles и готовый OSM-снимок в репозиторий не входят.

## 2. Возможности интерфейса

- Интерактивная Leaflet-карта с выбором точки, масштабированием, границей Ростовской области и переключением внешней/локальной подложки.
- Компоновка «Вариант A»: левый фрейм с вкладками **Точка / Пакетный поиск / Сохранённое** и карточкой текущей точки, карта в центре, правый фрейм с результатом дороги/километража, нижний статус-бар с быстрыми действиями. Единый однострочный блок поиска переносится между верхом карты и статус-баром настройкой «Положение блока поиска»; в нём есть чекбокс активации, иконки режимов, контекстное поле, переключатель зоны МСК и кнопка-лупа (дублируется Enter).
- Поиск адреса через Yandex: первое поле — населённый пункт, второе — улица и дом. Выбор подсказки только готовит черновик; координаты фиксирует кнопка «Поставить точку».
- Ручной ввод WGS84 с поддержкой десятичных градусов и DMS (`47°14'42.2"N 39°40'03.2"E`), синхронизация с МСК-61 и циклический выбор зоны/системы координат.
- Чекбокс «Режим поиска» активирует строку поиска, не блокируя карту; на время поиска блокируются пакетная загрузка и загрузка фото. После успешной загрузки фото поиск блокируется до «Очистить точку».
- Кнопка «Точка призрака» в статус-баре: при активном официальном километраже ползунок/поле км двигают зелёный клон, исходная красная точка остаётся; «Перейти» удаляет исходную точку, а призрак становится красным.
- Чтение координат из EXIF фотографии; одиночная загрузка также проходит через явное подтверждение точки.
- Пакетная загрузка фотографий с GPS EXIF во вкладке «Пакетный поиск»: редактируемые имена, удаление строк, «Показать все», режим перемещения одной выбранной точки (зелёный маркер, Сохранить/Отмена).
- Поиск ближайшей дороги по внешнему WFS СКДФ или локальной базе — источник дорог выбирается отдельно от источника адресных подсказок.
- Онлайн-поиск только трасс и дорог по названию или коду: подсказки появляются по мере ввода через серверную проверку линейного объекта/Ростовской области; результат можно выбрать из списка.
- Онлайн-километраж выбранной трассы: официальные участки `start_km`/`finish_km` из СКДФ WFS ограничиваются контуром области; точка выбирается вводом километра или ползунком. Ближайший километр считается проекцией на отрезок геометрии, а не по вершинам. Для точки, найденной через `/api/locate`, участки подгружаются автоматически при наличии `road_code`, после чего ползунок синхронизируется с этой точкой.
- Локальный поиск дороги по имени/коду и километражу, если установлена SQLite-база с подготовленными данными.
- Предварительный калькулятор WGS84 ↔ МСК-61: направление, зона 1–3, вычислительный профиль, копирование результата; размещение рассчитанной точки требует отдельного подтверждения.
- Обратный геокодер Yandex для выбранной точки: адрес (до дома) и район; при отсутствии ключа поля остаются «не определено».
- Учетные записи `admin`/`editor`; только администратор управляет пользователями.
- Персональные настройки, рабочая сессия (карта, вкладки, активная точка, пакетный список) и закладки хранятся на сервере и восстанавливаются при следующем входе.

### Важные ограничения поиска

Онлайн-подсказки и геокодирование используют Yandex API. Введённый адрес покидает приложение и передаётся Яндексу; backend проксирует запрос, чтобы API-ключ не находился в браузере. Поисковое окно задано прямоугольным bbox по крайним точкам контура Ростовской области (`38.22075,45.951688 — 44.319992,50.214477`); это уменьшает выдачу за пределами региона, но прямоугольник всё равно не является точным административным полигоном. Выбранный результат дополнительно проверяется по координатам и компоненту `province/area` в ответе геокодера. Для дорожного режима дополнительно принимаются только `kind=street` (в Геокодере так представлены линейные дороги), а без кода — только названия с дорожными терминами (`дорога`, `трасса`, `шоссе`, `магистраль`, `тракт`, `обход`, `подъезд`, `развязка`).

Слой СКДФ и адресный геокодер — разные источники и решают разные задачи. Переключатель дорожных данных не меняет источник адресных подсказок. OSM не предоставляет официальный километраж дороги: для локального поиска «дорога + км» необходимы данные с проверенной линейной привязкой.

## 3. Архитектура

```text
Браузер
  ├─ Leaflet UI: static/index.html
  ├─ Leaflet 1.9.4 и dom-to-image-more (локально из static/vendor)
  └─ same-origin HTTP + cookie-сессия
          │
          ▼
FastAPI / Uvicorn: src/main.py
  ├─ auth.py             — пользователи, хеши паролей, cookie-сессии
  ├─ batch.py            — обработка EXIF фотографий / batch upload
  ├─ WFS СКДФ           — внешняя дорожная геометрия
  ├─ OSM Overpass       — приблизительная ось дороги при отсутствии СКДФ
  ├─ Yandex Geocoder     — серверный proxy координат выбранного адреса
  ├─ /api/maps-config    — после auth отдаёт только client keys JS API/Geosuggest (no-store)
  ├─ offline_geo         — подключаемый локальный адресно-дорожный индекс
  ├─ msk61.py            — предварительные координатные преобразования
  └─ MBTiles             — необязательный локальный растровый сервер тайлов
```

### Основные подсистемы

**Backend — Python/FastAPI.** Валидирует запросы через Pydantic, обслуживает HTML, API авторизации, поиск дорог, онлайн-адресный proxy, координатные преобразования, EXIF, bookmarks и tiles. `httpx` используется для исходящих HTTP-запросов.

**Frontend — HTML/CSS/JavaScript.** Одностраничный интерфейс находится в корневом `static/index.html`. Leaflet управляет картой и слоями. Запросы к приложению идут через `apiFetch()` и включают cookie текущей сессии.

**Пакет `packages/offline_geo`.** Самостоятельный Python-модуль, независимый от FastAPI. Использует SQLite, FTS5 и Python standard library для подготовленного локального индекса населённых пунктов, улиц, домов и дорог. Schema v5 добавляет `road_segments` и `road_segments_rtree`: `nearest_road()` сначала получает кандидатов по bbox, затем точно проецирует точку и считает километраж. Индексы v4 остаются читаемыми через линейный fallback.

**Хранение.** Учётные записи/сессии, персональные настройки, рабочая сессия, история и закладки — SQLite (`src/users.db`). Общий `src/user_settings.json` хранит только настройки скриншота; `last_point` больше не используется. Выбор источников и тема дополнительно кэшируются в localStorage. SQLite-поиск и MBTiles — отдельные локальные файлы, путь можно вынести из checkout.

**PostgreSQL/PostGIS.** В локальной среде они установлены, но активная версия приложения их не использует; для работы обязательными не являются.

## 4. Потоки обработки

### 4.1 Поиск адреса

1. После входа пользователь вводит адрес в поле поиска.
2. Frontend получает из auth-protected `/api/maps-config` два client keys и динамически загружает Yandex JS API 2.1 с `apikey` и `suggest_apikey`; Geosuggest создаёт dropdown через `SuggestView` и ограничивается окном Ростовской области.
3. JS API и Geosuggest keys видны браузеру после входа, поэтому они должны быть ограничены точным hostname/продуктом в кабинете Яндекса. Endpoint config помечен `Cache-Control: no-store`. Ключ Geocoder не выдаётся браузеру.
4. После выбора подсказки её текст отправляется POST-запросом на server-side `/api/address/online/geocode`. Сервер ограничивает поиск Ростовской областью, валидирует координаты и компонент региона, возвращает координаты и точность геокодера.
5. UI ставит выбранную точку и запускает штатный поиск ближайшей дороги. Ошибка загрузки SuggestView, отсутствие ключей или геокодера отображаются явно; fallback на SQLite не выполняется.

### 4.2 Определение ближайшей дороги

- **Внешний источник:** `/api/locate` формирует ограниченную bbox-область по радиусу, запрашивает WFS слой `skdf_open:lyr_road_by_value_line`, проецирует точку на доступные линейные геометрии, отбрасывает кандидатов за пределами радиуса и выбирает ближайшего. Ошибка WFS возвращается как gateway error, а не маскируется сообщением «дорога не найдена». За один `/api/locate` используется `max_features=50`; в WFS-helper задан защитный потолок 10 000 объектов. Полнота выборки/пагинации для всего региона не подтверждена.
- **Локальный источник:** при `use_local=true` или включённом `ALBION_OFFLINE` backend открывает `offline_geo.sqlite3` и вычисляет ближайший дорожный сегмент. Если локальная БД не установлена, возвращается ошибка 503 — автоматического переключения на WFS нет.
- Интерполированный километраж достоверен настолько, насколько корректны начальный/конечный километры и порядок геометрии. Сторона дороги для локального ближайшего индекса неизвестна. Для OSM-геометрии официальный км не синтезируется.

### 4.2.1 Километраж выбранной трассы по СКДФ

1. После выбора результата онлайн-поиска с кодом дороги (`road_code`) UI вызывает auth-protected `POST /api/roads/online/sections` с этим кодом.
2. Backend запрашивает WFS слой `skdf_open:lyr_road_by_value_line` через `CQL_FILTER` с `BBOX(geom,38.22075,45.951688,44.319992,50.214477,'EPSG:4326')` и префиксом `road_name`. `bbox` и `CQL_FILTER` одновременно не передаются.
3. Каждый feature проверяется по точному коду дороги и по контуру `static/rostov_boundary.geojson`: участок принимается, только если все его вершины находятся внутри Ростовской области. Это исключает участки М-4 в Воронежской области и Краснодарском крае.
4. Ответ содержит `first_km`, `last_km`, диапазон и упорядоченные участки с `start_km`, `finish_km` и координатами. Если для дороги нет участков (например, `А-280` в текущем публичном слое), возвращается 404 с явным сообщением.
5. Блок официального километража активируется отдельным чекбоксом и по умолчанию не содержит данных. После активации UI переводит ползунок `0…(last_km − first_km)` в официальный километр и интерполирует координату по геометрии выбранного участка. Поле принимает `829+500` или `829.5`; ввод/ползунок двигают точку вдоль трассы, а новая точка пересчитывает км по проекции на участки СКДФ.
6. В WFS встречаются перекрывающиеся старые/новые начертания с одинаковым километражом. UI выбирает участок, ближайший к исходной точке Яндекса, вместо произвольного первого совпадения.
7. Километраж СКДФ не является заменой геодезической линейной привязки: он зависит от полноты слоя, качества `start_km`/`finish_km` и порядка геометрии. Официальный километр для отсутствующих дорог и пробелов не синтезируется.
8. Если СКДФ вернул 404 (например, `60К-31`), UI вызывает `POST /api/roads/overpass/geometry`: сервер собирает OSM-way с точным `ref` в связанную ось, строит относительную шкалу `0…длина` и возвращает кандидатов. UI рисует оранжевую пунктирную линию, маркеры начала/конца и позволяет кликом по линии выбрать км и поставить точку. Это приблизительный сценарий: он не является официальным километражем и явно помечается в интерфейсе.

### 4.3 МСК-61

- `POST /api/msk61/from-geographic`: широта/долгота → координаты МСК-61 `X/Y`.
- `POST /api/msk61/to-geographic`: `X/Y` МСК-61 → широта/долгота.
- `X` — северная координата, `Y` — восточная; обе в метрах. WGS84 вход задаётся как `lat`, затем `lon` в десятичных градусах.
- Зона (1–3) задаётся явно. Профиль `calculated` выполняет проекцию без преобразования датума; географический результат не должен считаться подтверждённым WGS84. Профиль `gost_51794_2008` применяет заданные параметры Helmert-преобразования при нулевой высоте, но местная точность не подтверждена.
- Рядом с селектором зоны есть справка с опубликованным распределением кадастровых районов и кодов по зонам из [статьи «Территория ГИС»](https://terraingis.ru/msk-61.html), опубликованной 30.07.2020 и обновлённой 17.08.2023. Это открытая профильная публикация, не первичный документ Росреестра.
- Все вычисления отмечены как предварительные. Программные round-trip тесты подтверждают численную обратимость формул, но не кадастровую/геодезическую точность; параметры следует сверять с исходной координатной ведомостью или официальным ключом перехода.
- Численная сверка через Playwright с калькулятором [GeoBridge](https://geobridge.ru/proj) (2026-10-18) для точек зон 1–3 показала: профиль `gost_51794_2008` совпадает с `EPSG:6336101/102/103` в пределах 0.001 м в прямом направлении и около 0.0003 м в обратном; профиль `calculated` расходится примерно на 105–114 м, в основном по восточной координате. Поэтому в UI профиль ГОСТ выбран по умолчанию. Это сверка с третьей стороной, а не официальная геодезическая аттестация: GeoBridge сам предупреждает о непригодности для геодезических работ, а локальный статус остаётся `preliminary_unverified`.

### 4.4 Фотографии и batch

Одиночный и пакетный endpoint читают EXIF JPEG/TIFF, валидируют координаты GPS и возвращают широту/долготу. Для batch установлены лимиты: максимум 50 файлов, до 12 MiB на файл и до 100 MiB на запрос. Фотография без GPS не приводит к остановке всего пакета — ошибка указывается для соответствующего файла.

## 5. Интерфейс API

Все API, кроме `/api/health` и `/api/auth/login`, требуют действительную сессию.

| Endpoint | Назначение |
|---|---|
| `GET /` | Основной UI; HTML выдаётся с `Cache-Control: no-store`. |
| `GET /api/health` | Минимальный статус сервера; не тестирует внешние зависимости. |
| `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me` | Вход, выход и сведения о текущем пользователе. |
| `POST /api/auth/change-credentials` | Смена собственных credentials. |
| `GET/POST/PATCH /api/users...` | Список, создание и изменение пользователей; администраторская роль. |
| `POST /api/exif`, `POST /api/batch/upload` | Извлечение GPS из одной/нескольких фотографий. |
| `POST /api/locate` | Поиск ближайшей дороги из явно выбранного внешнего или локального источника. |
| `POST /api/address/online/suggest`, `POST /api/address/online/geocode` | Yandex autocomplete и разрешение выбранной подсказки в координаты. |
| `POST /api/geocode/reverse` | Обратный геокодер: координаты → адрес (до дома) и район; требует настроенный `YANDEX_API_KEY`. |
| `GET/PUT/DELETE /api/user/preferences`, `GET/PUT/DELETE /api/user/workspace` | Персональные настройки и рабочая сессия с версионированием; конфликт устаревшей версии — 409. |
| `POST /api/roads/online/search` | Поиск дороги/трассы через Yandex Geocoder; проверяет код дороги и регион, возвращает координаты объекта. |
| `POST /api/roads/online/sections` | Официальные участки СКДФ с `start_km`/`finish_km`, ограниченные контуром Ростовской области; 404 без километража. |
| `POST /api/roads/overpass/geometry` | Приблизительная ось дороги из OSM Overpass по `ref`: связанные way, относительный километраж, кандидаты по названию/близости. |
| `GET /api/address/suggest`, `GET /api/roads/search` | Локальные подсказки и поиск дорожного/цепного километража. Требуют заранее подготовленный индекс. |
| `POST /api/msk61/from-geographic`, `POST /api/msk61/to-geographic` | Двухсторонние предварительные преобразования МСК-61; профиль по умолчанию `gost_51794_2008`. |
| `GET /api/data-sources` | Наличие локальной SQLite/MBTiles и Boolean-статусы настройки ключей, без выдачи секретов. |
| `GET /tiles/{z}/{x}/{y}.png` | Необязательная отдача PNG тайла из MBTiles в XYZ-порядке. |
| `GET/POST/PATCH/DELETE /api/bookmarks...` | Персональные закладки пользователя: список, создание, переименование, удаление. |
| `GET/POST /api/screenshot-settings`, `POST /api/save-screenshot` | Настройки снимка и сохранение проверенного PNG в каталог приложения. |
| `GET /static/rostov_boundary.geojson`, `GET /static/js/geo-core.js` | Граница для карты и клиентское гео-ядро; прочие файлы `static/` напрямую не публикуются. |

Подробные JSON-схемы доступны у запущенного FastAPI по `/docs` и `/openapi.json`.

## 7. Технические требования

### Программная среда

- Linux x86-64 предпочтителен; текущий проект ориентирован на локальный Linux deployment.
- Python **3.11+** и `uv` для создания venv/установки зависимостей.
- Зависимости backend перечислены в `requirements.txt`: FastAPI, Uvicorn, HTTPX, Pillow, piexif, Pydantic, python-multipart, python-dotenv.
- Для тестов дополнительно установить `requirements-dev.txt`.
- Интернет необходим текущему полному пользовательскому сценарию: OSM tiles, SKДФ WFS и Yandex Geosuggest/Geocoder. JS/CSS Leaflet и dom-to-image загружаются локально.
- Для локального поиска используется встроенная SQLite с поддержкой FTS5. PostgreSQL, Redis, GPU и Node.js для запуска не требуются.
- Для реального OSM PBF импорта отдельно нужны optional Python-пакет `osmium`, системная CLI `osmium` и подходящий PBF/проверенный polygon boundary. Для обновления PBF требуется дополнительная `pyosmium-up-to-date`. Код importer есть, но настоящий региональный import/coverage QA в этой среде ещё не проходил.
- Для адресации нужны `YANDEX_JS_API_KEY` (JavaScript API) и `YANDEX_SUGGEST_API_KEY` (Geosuggest): оба ключа передаются браузеру только после входа, должны быть ограничены точным доменом приложения. `YANDEX_API_KEY` (Geocoder/reverse-geocoding) остаётся server-only. Ключи должны быть активированы у Яндекса; после изменения `.env` или environment перезапустить процесс.

### Ориентир по железу

Формальные нагрузочные тесты не проводились, поэтому значения ниже — **планировочная оценка**, а не измеренная минимальная конфигурация.

| Сценарий | Практический ориентир |
|---|---|
| Запуск приложения, внешние сервисы, 1–несколько пользователей | 2 vCPU, 4 GB RAM, 20–40 GB SSD/VPS. |
| Локальная сеть с подготовленным SQLite и MBTiles Ростовской области | 4 CPU cores, 16 GB RAM, NVMe от 500 GB; итоговый размер tiles зависит от масштаба/детализации. |
| Импорт/пересборка OSM и хранение подробной карты на одной машине | 6–8 CPU cores, 32 GB RAM, NVMe 500 GB–1 TB как комфортный запас. |

GPU не требуется. Для офлайн-данных нужно отдельно хранить резервную копию SQLite/MBTiles и описывать источник, дату снимка, покрытие, лицензию и атрибуцию.

## 8. Установка и запуск

Из корня checkout:

```bash
uv venv .venv
uv pip install --python .venv/bin/python -r requirements.txt
.venv/bin/python -m uvicorn main:app --app-dir src --host 127.0.0.1 --port 8021
```

Открыть `http://127.0.0.1:8021/`. Для разработки тесты запускаются так:

```bash
uv pip install --python .venv/bin/python -r requirements-dev.txt
.venv/bin/pytest -q
```

Существующая локальная установка использует пользовательский systemd unit `albion-locator-autonom.service` и loopback. При публикации через reverse proxy дополнительно нужно настроить HTTPS, cookie security и допустимый Origin; текущий code path не задаёт `Secure` флаг cookie, что требуется учесть перед внешним/интернет-доступом.

## 10. Авторизация и безопасность

- Неаутентифицированному пользователю доступна форма входа; API защищены cookie-сессией, кроме health/login.
- Начальный пользователь: `админ` / `альбион`. Пароль следует сменить при первом входе и создать индивидуальные учётные записи.
- Пароли хранятся как salted PBKDF2-HMAC-SHA256 hash; session token хранится в БД в hashed виде. Cookie HttpOnly, SameSite=Lax, TTL 30 дней.
- Роль `admin` управляет users, роль `editor` предназначена для обычной работы.
- Upload/PNG маршруты имеют размерные и форматные ограничения; экранные файлы сохраняются только в заданном каталоге.
- Search text адреса передаётся внешнему провайдеру. Не включать содержание адресов/ключи в логи.
- Ограничение частоты онлайн адресных запросов в текущем backend — внутрипроцессное, per-user; для нескольких worker-процессов или публичного развёртывания дополнительно нужен proxy/API-level rate limiter.
- Перед доступом из интернета сменить стартовый пароль, настроить HTTPS и безопасные cookies, проверить CloudPub/reverse proxy headers/Origin, отозвать известные ранее опубликованные ключи и задать новые в secrets environment.

## 11. Текущая готовность и незавершённые части

**Реализованы:** FastAPI приложение и UI, пользовательская auth, внешний WFS nearest-road flow, онлайн address UI/proxy, онлайн поиск дорог/трасс, километраж выбранной трассы по официальным участкам СКДФ внутри контура области, двусторонняя предварительная MSK UI/backend, самостоятельный SQLite search/index builder, API подключения локальной SQLite/MBTiles, тестируемый код PBF importer и atomic update helpers, exports/importers для переданных SKДФ схем, защищённое сохранение PNG/EXIF.

**Не поставлены/не подтверждены:**

1. Нет локального регионального SQLite index, OSM PBF и MBTiles; OSM-тайлы остаются сетевыми.
2. Настройка ключей Yandex зависит от target deployment и права/quota двух API; наличие одного ключа не предполагает доступ к обоим продуктам.
3. Реальный OSM importer не обкатан на полном региональном PBF; current candidate boundary и data coverage должны пройти независимую проверку до production.
4. Доступ к feature `geo_road_axis_lr` СКДФ публично не подтверждён; bulk-use/cache rights СКДФ требуют отдельного юридического разрешения.
5. OSM roads не обеспечивают официальный chainage. Онлайн-километраж доступен только там, где публичный слой СКДФ содержит `start_km`/`finish_km`: например, проверены `М-4` и `Р-280`, но `А-280` в текущей выборке отсутствует. Перекрывающиеся старые/новые начертания и пробелы требуют проверки; для отсутствующих дорог официальный км не синтезируется. Вместо него может строиться отдельная приблизительная ось OSM с относительным километражем (Overpass), которая не считается официальной.
6. У МСК-61 расчёта отсутствует независимая верификация параметров по официальному региональному источнику и контрольным пунктам. Применять полученные координаты для кадастровой/геодезической документации без проверки нельзя.
7. Полностью offline E2E на подготовленном региональном индексе не проводился; browser E2E покрывает UI-состояния на изолированном сервере, визуальная ручная QA остаётся отдельным шагом.

## 12. Проверки и поддержка

На текущей ветке полный набор `pytest` проходил: 140 tests (включая 52 теста `offline_geo`). Клиентское гео-ядро покрыто 24 тестами Bun (`bun test tests/js`). Browser E2E: 29 Playwright-сценариев (`tests/e2e`), отдельный CI job. Внешние Yandex/WFS сервисы в pytest замещаются mock-ответами; это проверяет контракт/ошибки, не подтверждает работоспособность конкретного deployment API key. Отдельно выполнялась live-проверка `/api/roads/online/sections` против публичного СКДФ WFS: `М-4` — 647 участков, 826.3–1154.5 км; `Р-280` — 40 участков, 5.67–119.0 км; `А-280` — 404 без километража. Live-проверка дорожного поиска через Yandex: `М-4 Дон` и `Р-280` дают по одной дороге, `Ростов-на-Дону` и `улица Ленина` — 404. UI дополнительно проверялся в headless Chrome через CDP: вкладки, режимы, блокировка ползунка, обратный геокодер и восстановление сессии после перезагрузки.

Обновление кода выполняется через Git. Геоданные и архивы должны обновляться отдельной процедурой, с резервной копией, manifest с датой/лицензией, QA покрытия и проверкой SQLite integrity. Периодическое OSM обновление не запланировано автоматически.
