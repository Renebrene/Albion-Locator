# Runtime performance: память и CPU

**Дата:** 19.10.2026  
**Среда:** локальная машина, Linux; Chromium 155 headless (1440×900); изолированный uvicorn с временной SQLite-БД и отключёнными Yandex-ключами. Live-сервис на `127.0.0.1:8021` измерялся отдельно.

## Backend

### Idle и live

| Показатель | Значение |
|---|---:|
| Live systemd RSS | **38.8 MB** |
| Live CPU за 24 мин | **1.305 s** (~0.09% одного ядра) |
| Изолированный старт | 58.3 MB RSS, 5 потоков |
| Idle 10 s (изолированный) | 0% CPU, RSS не меняется |
| RSS после ~2 100 запросов | 59.0 MB (+0.7 MB, без роста после прогрева) |

Live-процесс имеет меньший RSS, чем свежий изолированный старт; разница объясняется разным моментом прогрева/аллокатора, а не утечкой.

### Нагрузка (20 параллельных клиентов)

| Endpoint | Запросов | RPS | p50 | p95 | CPU (одно ядро) | RSS |
|---|---:|---:|---:|---:|---:|---:|
| `GET /api/health` | 500 | 1549 | 9.4 ms | 19.1 ms | 43% | 58.5 MB |
| `GET /api/auth/me` | 500 | 1391 | 11.1 ms | 19.6 ms | 86% | 58.6 MB |
| `POST /api/msk61/from-geographic` | 300 | 1311 | 12.4 ms | 19.9 ms | 92% | 59.0 MB |
| `GET /api/user/preferences` | 500 | 1117 | 17.6 ms | 18.7 ms | 101% | 59.0 MB |
| `PUT /api/user/preferences` | 300 | 1087 | 17.6 ms | 19.4 ms | 98% | 59.0 MB |

Выводы:
- Idle-нагрузка практически нулевая.
- Один uvicorn-процесс упирается в одно ядро примерно на 1.1–1.5k простых запросов/с; это ожидаемо для single-worker event loop.
- Утечки памяти под нагрузкой не видно: RSS стабилизируется около 59 MB.
- `/api/locate` намеренно не нагружался: он ходит в внешний WFS/Yandex, и массовый тест создал бы нагрузку на провайдера, а не на локальный backend.

## Browser UI

Измерения через Playwright/CDP. Для памяти использовались **PSS/USS**, а не суммарный RSS: сумма RSS по процессам Chrome завышает результат из-за общих страниц.

| Показатель | Значение |
|---|---:|
| Процессов Chrome (headless) | 5 |
| PSS всего браузера | **~193 MB** |
| USS всего браузера | ~104 MB |
| JS heap после входа | 3.77 MB |
| DOM nodes | 1377 |
| Idle 10 s: heap/nodes | 0 / 0 |
| Idle 10 s: CPU | ~0.5% одного ядра |
| API-запросов за 10 s idle | 0 |
| 120 циклов переключения позиции/режима/подсказок | heap **+0.06 MB**, nodes **+1**, API-запросов **3** |
| CPU на 120 циклов | ~0.03 s task, 0.012 s script |
| PSS после стресса | без роста (в пределах шума) |

Выводы:
- JS heap и DOM не растут заметно; признаков утечки от переключения режимов/позиции нет.
- Автосохранение состояния дебаунсится: 120 изменений дали 3 API-запроса, а не 240.
- Основная память — не JS-приложение (3.8 MB), а процессы Chromium (renderer/GPU/utility); в headed-режиме с GPU и расширениями PSS будет выше.
- Карта с OSM-тайлами не создаёт фоновой CPU-нагрузки после загрузки.

## Рекомендации

1. Для production-мониторинга использовать **PSS/RSS процесса uvicorn и cgroup memory**, а не только systemd `Memory`; для браузера — PSS, не сумму RSS.
2. Single-worker FastAPI достаточен для текущей локальной нагрузки; при публикации в LAN/Internet измерять под реальным профилем и при необходимости добавить worker/proxy.
3. Не увеличивать частоту автосохранения: текущий debounce эффективен; при добавлении новых `scheduleStateSave()` проверить, что они не создают шторм PUT-запросов.
4. Повторить browser-замеры в headed Chromium/Firefox с реальными расширениями и GPU; headless-профиль даёт нижнюю оценку.
5. Внешние WFS/Yandex измерять отдельно с учётом квот и не включать в локальный load-test.
